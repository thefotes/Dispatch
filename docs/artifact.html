Six agents, six keys

The plan was to give each running coding agent its own key on a Work Louder Creator Micro 2, lit with that agent's live status. It took a wrong conclusion, a firmware update, twelve experiments and a second SDK hidden inside a different application — but it works.

The answer

Individual keys are addressed through a vendor RPC that the Work Louder Input app never calls. It lives in @worklouder/device-kit-oai — a second, separate SDK that ships inside the Codex desktop app, not the configurator. 

// per-key: params are a bare ARRAY, one entry per key
{
  "method": "v.oai.thstatus",
  "params": [
    { "id": 0, "c": 16755200, "b": 1, "e": 1, "s": 0.5 },   // key 0, amber, solid
    { "id": 1, "c": 16723501, "b": 1, "e": 4, "s": 0.5 },   // key 1, red, breathing
    { "id": 2, "b": 0, "e": 0 }                             // key 2, off
  ]
}
FieldMeaning
idKey index — 0-based, row-major over the pad's [2, 4, 4, 3] matrix.
cPacked RGB integer.
bBrightness, 0–1.
eEffect as a number: 0 off, 1 solid, 2 snake, 3 rainbow, 4 breath, 5 gradient, 6 shallow breath.
sSpeed, 0–1.
sk / sa1/0 — mirror this entry onto the whole keys / ambient zone. Optional; colours apply without them.

Why it stayed hidden

Two details, and both fail silently — the firmware answers {"ok":1} to any payload you send it, including deliberately malformed ones. A wrong guess is indistinguishable from a right one except by looking at the LEDs.

Field names c   b   e   s   m Abbreviated on the wire — not the full color, brightness, effect that the documented lights.preview call uses.
Effect type 1 An integer, not the effect string the same firmware accepts on lights.preview. Two calls, two conventions.

Every earlier attempt sent full field names and string effects. The handler parsed what it recognised, ignored the rest, and cheerfully reported success.

Two things that will bite you

Thread state overrides the zones

Clearing keys and ambient does not turn the pad off if any thread is still set — thread colour paints over zone colour. A cleanup routine that only clears the zones leaves the pad glowing, which is exactly what happened here. Clear both.

Open the HID device shared, not seized

hidapi seizes by default. This pad puts its vendor collection on the same IOHIDDevice as its keyboard collection, and macOS refuses to let anything seize a keyboard — so the open fails with 0xE00002C1, which reads exactly like a missing Input Monitoring grant and isn't. Pass nonExclusive. You then coexist with the vendor's own apps rather than fighting them for the device.

The thing we nearly did instead

Rewriting the pad's board identity

Before finding the real answer, the evidence pointed hard at variant gating: some v.oai.* handlers answered while others returned Method not found, which looked like one firmware image shipping different handler sets per board. The next step would have been writing /fs/board_info.json to declare a different vendor and variant, since the firmware prefers that file over eFuse.

We declined, on the grounds that the correct integers were undocumented, a wrong pair would make the pad claim to be hardware it isn't, and the recovery path runs through a device that may no longer enumerate as expected. That call turned out to be right for a better reason than the one we had: the gating theory was wrong. v.oai.hid and v.oai.rad aren't missing handlers at all — they're notification channels the device pushes to the host, and were never callable. The capability was never gated. It was just undocumented.

Which is the useful lesson: a tidy theory built on a misread error message will happily survive a lot of evidence. Reading the vendor's own client was worth more than every inference drawn from the outside.

All testing was done against our own device for interoperability, using publicly downloadable firmware images and the shipped desktop applications. No firmware was modified. The device keymap was backed up before any write and verified restored afterwards.
