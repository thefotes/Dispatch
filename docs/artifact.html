Hardware investigation · negative result

Six agents, six keys, one colour

The plan was to give each running coding agent its own key on a Work Louder Creator Micro 2, lit with that agent's live status. The keys are individually addressable in hardware. The firmware contains the code that does it. Neither fact turned out to be enough.

What we were building

Several coding agents run in parallel in a terminal workspace. Each is either working, blocked waiting on input, idle, or done. The pad was going to be the physical dashboard for them.

The firmware describes this pad as a [2, 4, 4, 3] matrix. The highlighted six were to become agents 1–6.

Press a key → jump to that agent's session.
Key colour → that agent's live status.

Half of it works perfectly. The pad sends F13–F24, the host binds them, and pressing a key jumps straight to the right session. It was only ever the lighting half that was in question.

What the host can actually drive

The device speaks JSON-RPC 2.0 over raw HID. Exactly one lighting call reaches it, and it addresses two whole-device surfaces — not keys: 

// works: two surfaces, one colour each, effects honoured
{
  "method": "lights.preview",
  "params": {
    "backlight": { "effect": "solid", "brightness": 1, "color": 16711680 },
    "underglow": { "effect": "breath", "brightness": 1, "color": 255 }
  }
}

So the shipped result is one aggregate colour across both surfaces: red breathing when any agent needs you, amber while any is working, green when everything is idle. That answers “does anything need me?” at a glance, which is most of the value. It just isn't per-agent.

What the gating looks like

The per-key capability is present but switched off, and one asymmetry gives it away. On the same device, in the same session:

v.oai.rgbcfg {"ok":1} Registered. Accepts any payload. Does nothing.
v.oai.thstatus {"ok":1} Registered. Accepts any payload. Does nothing.
v.oai.hid Method not found Not registered on this variant at all.

A device that registers some of a feature's handlers and not others is a device running a build that decides, at boot, which variant it is. Board identity comes from eFuse. The stubs answer politely; the real implementations aren't there.

Everything else corroborates it. The Codex Micro drives five per-key agent states — idle, thinking, complete, needs input, error — from this same firmware family, and its own keycode table (KV_OAI_AG00…AG19) is present in the image on our device too. Meanwhile press coverage of the Codex Micro notes the Agent Keys only work with the ChatGPT desktop app acting as the bridge. This is a closed integration, not an unfinished one.

What we didn't try, and why

Rewriting the pad's board identity

The firmware reads its vendor and variant from eFuse — but it prefers /fs/board_info.json when that file exists, logging “not found, falling back to eFuse” when it doesn't. That file is absent on this device, and the filesystem is writable over the same HID channel we were already using. Writing one to declare the OAI vendor and variant is the one remaining lever that could plausibly flip the real handlers on.

We stopped there deliberately. The correct integers are undocumented, and there is no safe way to discover them — only disassembling Xtensa firmware or brute-forcing values on a live device. A wrong pair makes the pad claim to be hardware it isn't, which plausibly affects BLE pairing, the USB product ID, and how the configurator treats it. That is a real bricking risk on someone's daily driver, spent on a speculative payoff that might still require the ChatGPT desktop bridge to do anything.

It is reversible in principle — delete the file, fall back to eFuse. “In principle” is doing a lot of work in that sentence, and the recovery path runs through a device that may no longer enumerate the way you expect.

Two things worth knowing if you attempt this

Neither is documented anywhere, and both cost real time to find.

Open the HID device shared, not seized

hidapi seizes by default. This pad puts its vendor collection on the same IOHIDDevice as its keyboard collection, and macOS refuses to let anything seize a keyboard — so the open fails with 0xE00002C1, which reads exactly like a missing Input Monitoring grant and isn't. Pass nonExclusive. As a bonus, you then coexist with the vendor's own app instead of fighting it for the device.

The framing

// 64-byte reports, usage page 0xFF00 / usage 1
byte 0      report id, always 0x06
byte 1      channel: 1 = firmware debug log, 2 = JSON-RPC
byte 2      payload length in this report, max 61
bytes 3..   UTF-8 fragment of the JSON message

// colours are 0xRRGGBB integers; brightness/speed/magic are 0..1 floats
// call ids must be < 1000, or firmware ignores the request

Where it landed

Six keys that jump to six agents, and one status colour across both lighting surfaces instead of six individual ones.

The honest summary is that the hardware can do what we wanted and the firmware knows how, but the path from a host application to an individual LED is closed on this variant. Not missing — closed. A documented report format, however minimal and unsupported, would be enough to open it.

All testing was done against our own device for interoperability, using publicly downloadable firmware images and the shipped configurator. No firmware was modified. The device keymap was backed up before any write and verified restored afterwards.
